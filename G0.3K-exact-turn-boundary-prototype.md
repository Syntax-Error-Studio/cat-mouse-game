## 0. Design Audit (A–E) — Conclusions with Code Evidence

### A. Chance structure preserved (DECISION → CHANCE → DECISION)

**Conclusion: PASS — the DAG keeps chance nodes as first-class nodes INSIDE the macro turn.**

Evidence: `simulateSearchAction` (simulator.ts) builds a CHANCE node only when a
`mouseStep` consumes a butter (`pickedButter`); the outcomes are the legal
re-spawn cells (uniform weight via `buildButterChance`). The mouse MUST continue
its turn after picking up butter, so flattening boundaries into one MIN choice
would turn a stochastic outcome into a player choice. The DAG therefore emits
`DECISION → CHANCE → DECISION`.

**Implementation catch (fixed):** two DIFFERENT `mouseStep` actions consuming
butter from the same state can have DIFFERENT outcome pools (different eaten
butter cell ⇒ different legal spawn set). The CHANCE node identity therefore
includes the triggering ACTION, not just the state — `chanceKey =
stateKey#cost#actionSignature`. A naive merge on (state,cost) would mix outcome
pools. The frontier equivalence gate (below) verifies this: g4t2→MOUSE has
exactly 6 CHANCE nodes and the total probability matches the legacy oracle.

### B. mateActionCost identity

**Conclusion: PASS — dedup identity = `stateKey # cumulativeCost`; states reached
via different cumulative costs are kept separate.**

Evidence: `mateActionCost` (expectiminimax.ts): catStep=1, mouseStep=1,
catPlaceTrap=0, mouseSkill=0, chooseTunnel=0. A TURN_BOUNDARY reached with cost
2 vs cost 3 carries a different mate distance; merging them would corrupt
`stepScore`/`unstepScore` (branch value attributed the wrong distance). The
prototype's `nodeKey = stateKey#cost` preserves this, and the frontier gate
verifies per-boundary cost matches the legacy oracle (e.g. g4t2 mouse: cost3:43,
cost6:5082 — preserved).

### C. Repetition semantics

**Conclusion: PASS for d1/d2 (vacuously), preserved via ancestorClosure for d3+.**

Evidence: `stateKey` (transposition.ts) includes `currentPlayer`. After a
cat→mouse switch, mouse-turn stateKeys are DIFFERENT keys (currentPlayer=mouse),
so a cat-turn atomic state can never re-appear on a mouse-turn path — a
cross-turn repetition hit at d1/d2 is IMPOSSIBLE. G0.3J measured reps=0 on all
26 roots. For d3+ (cat→mouse→cat) the DAG carries `ancestorClosure` (union of
stateKeys on any path to a node) and the turn-boundary search uses it
conservatively. At d1/d2 the closures never fire, matching the atomic search
bit-for-bit (verified: no repetition discrepancies in the truth gate).

### D. Terminals are recorded where they occur

**Conclusion: PASS — TERMINAL nodes are emitted AT the point of capture/
hole-entry; the macro turn is NOT force-completed.**

Evidence: `catMove`→`checkCatWin` and `applyMouseStepCore` (hole entry with
butter→MouseWins) flip the phase immediately. The DAG builder checks
`next.phase` on every child and emits a TERMINAL node without generating further
actions. Frontier gate verifies terminal state+cost sets match the legacy oracle
(g3t5→MOUSE has exactly 1 terminal in both).

### E. Immediate turn-ending rules are real boundaries

**Conclusion: PASS — trap-step and tunnel-exit produce genuine TURN_BOUNDARY
nodes.**

Evidence: a mouse trap-step flips `currentPlayer` to Cat inside
`applyMouseStepCore` (simulator does NOT endTurn again); `chooseTunnelExit` →
`forceEndTurnIfNeeded` hands off with 0 moves. Both are `switched` transitions
⇒ DAG emits TURN_BOUNDARY, depth decrements there. Frontier gate verifies these
boundaries match the legacy oracle exactly.

**Note:** the prototype's `searchTurnBoundary` phase-1 has NO Alpha-Beta and NO
Transposition Table. It therefore expands ALL turn-end boundaries, so its
dagNodes at d2 (21K-220K) exceed the legacy's AB+TT-pruned node count (655-4,283).

the turn-boundary DAG (fewer, larger nodes), the node count should drop far below
the atomic search's (each DAG node is a whole turn, not one step).

## 5. Performance Gate (100/500ms) — deferred

The 100/500ms performance comparison was NOT completed because phase-1
`searchTurnBoundary` has no AB/TT and runs 6-170s per d2 root (g4t2 d2 = 168s,
g1t2 d2 = 69s, g5t1 d2 = 6.5s), vs legacy AB+TT 0.2-0.5s. A wall-clock comparison
at 100/500ms is meaningless until the prototype gains AB/TT. This is the explicit
next step for production integration.

## 8. Verdict

```
TURN_BOUNDARY_ARCHITECTURE = PROMISING_BUT_BLOCKED
```

**Why PROMISING:**
- Exactness is PROVEN: frontier equivalence (10/10), SearchValue bit-identical
  at d1 (10/10) and d2 (4/4, incl. all three priority roots).
- Compression is REAL: 2-30x per turn (mouse turns 13-30x), confirming G0.3J's
  diagnosis that atomic-action search wastes 53-97% of its work on within-turn
  duplication.
- Chance/trap/skill/tunnel semantics all preserved with no rule changes.

**Why BLOCKED (not READY):**
1. **Phase-1 has no Alpha-Beta / TT.** The prototype expands ALL turn-end
   boundaries (d2 = 21K-220K dagNodes, 6-170s), so it cannot yet demonstrate
   the wall-clock speedup. AB over the turn-boundary DAG (fewer, larger nodes)
   is the obvious missing piece.
2. **G0.3A/G0.3E plan-witness integration is not done.** The DAG retains
   atomic-action witnesses (so exact-primary tie handling remains possible),
   but forcedLossTieBreak / extractBestCatTurnPlan are not re-wired onto the
   turn-boundary result. Plan extraction must be implemented and verified
   before production use.
3. **Full 26-root d2 gate not run** (node-budget/time capped); the 4-root d2
   gate + 10-root d1 gate is strong evidence but not the complete corpus.

**Next step (not this phase):** add AB+TT over the turn-boundary DAG (the
DECISION/CHANCE resolver becomes the standard MAX/MIN/EXPECT loop with the
legacy comparator), re-integrate plan witnesses, then run the full 100/500ms
performance gate. Do NOT increase the production budget or touch production
search until that is proven faster.
