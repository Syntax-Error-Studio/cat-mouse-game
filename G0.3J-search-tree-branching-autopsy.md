## 6. Same-Turn vs Turn-Switch Nodes

The search's depth decrements only on turn switch (`depthTurns -= switched ? 1 : 0`). Within a single turn, all atomic actions are at the same depth. This means:

- **d1 = one cat turn**: entirely same-turn expansion (86-154 nodes, all MAX, no AB possible)
- **d2 = cat turn + mouse turn**: same-turn expansion for cat, then same-turn expansion for mouse at each cat boundary

The enumeration shows that within a single cat turn, the search expands 37-320 nodes to explore 64-821 raw sequences converging to 14-214 unique states. The within-turn expansion is where most of the work happens.

## 10. ATOMIC_ACTION_SEARCH_WITH_TURN_DEPTH

**ATOMIC_ACTION_SEARCH_WITH_TURN_DEPTH = YES — this is the primary structural reason for poor depth scaling.**

### Evidence

The search operates at atomic-action granularity (each node = one catStep/mouseStep/catPlaceTrap/mouseSkill/chooseTunnel), but depth is measured in turns (`depthTurns -= switched ? 1 : 0`). This means:

1. **"depth=1" = one full cat turn**: 4 catSteps + optional catPlaceTrap, producing 64-821 raw sequences (37-320 expanded nodes). No MIN nodes exist → AB is structurally useless (0% cutoffs at d1 for ALL roots).

2. **"depth=2" = full cat turn × full mouse turn**: The cat turn produces 14-214 unique boundary states. For EACH, the mouse turn produces 10-615 unique boundary states (80-12,288 raw sequences). The combined tree has 571-4,283 internal nodes (15-87x growth from d1).

3. **"depth=3" would multiply by another full turn** (~20-50x), reaching 10K-214K nodes. **"depth=4" reaches 135K-12M nodes.** Both are infeasible in 100-1000ms.

4. **The mouse turn is the dominant multiplier**: Mouse turns with butter produce 1,034-12,288 raw sequences (vs 64-821 for cat). The mouseSkill zero-cost action turns a 3-move turn into 6 moves, multiplying the tree ~27x.

5. **Massive within-turn duplication is wasted**: 53-97% of raw sequences within a turn converge to duplicate turn-end states. The search expands them all because it operates at atomic-action level — two different action orderings (e.g., move→trap vs trap→move) go through different intermediate states even though they reach the same end state.

### Why AB+TT+ordering can't fix this

- **AB**: Only works when there are MIN nodes to prune. At d1 (cat-only), there are none. At d2, AB works but the tree is already too large before pruning kicks in.
- **TT**: Catches intermediate-state transpositions (different paths reaching the same state with the same movesLeft), but NOT turn-end-state transpositions (different paths reaching the same end state via different intermediate states). The depth-mismatch rule prevents d1 entries from being reused at d2.
- **Move ordering**: Helps find good moves first (high first-move cutoff rate at d2), but can't eliminate the d1 structural problem (no MIN to cut against).

## 11. Recommended Architecture: TURN_BOUNDARY_STATE_COMPRESSION

### Concept

Replace the atomic-action search with a **turn-level search** where each "move" is a complete turn, not a single atomic action.

### Architecture Sketch (design only, not implemented)

```
TurnBoundarySearch(state, depthTurns):
  1. Identify current actor (cat or mouse)
  2. ENUMERATE all unique turn-end states:
     - BFS within the current actor's turn
     - At each step, apply each legal SearchAction via simulateSearchAction
     - Deduplicate by stateKey at EVERY step (not just at boundaries)
     - Stop expanding a branch when the actor switches (turn boundary)
     - Result: set of unique turn-end states + the best action sequence to each
  3. For each unique turn-end state:
     - If depthTurns <= 1: evaluate with evaluateForCat (leaf)
     - Else: recurse TurnBoundarySearch(turnEndState, depthTurns - 1)
  4. MAX/MIN selection over the unique turn-end states
     - Cat (MAX): pick the turn-end state with highest value
     - Mouse (MIN): pick the turn-end state with lowest value
  5. CHANCE: if any turn-end state involves butter regeneration,
     expand all chance outcomes (same as current)
```

### What this changes

| Aspect | Current (atomic) | Proposed (turn-boundary) |
|--------|-----------------|-------------------------|
| d1 = | 86-154 nodes, 214-347 leaves | 14-214 unique turn-end states, 14-214 evals |
| d2 = | 571-4,283 nodes, 82-5,212 leaves | 14-214 × 10-615 unique pairs, AB-pruned |
| d1 AB | 0% cutoffs (no MIN) | Effective (MIN at d2, MAX at d1) |
| Within-turn dup | Expanded redundantly | Eliminated (dedup at every BFS step) |
| Per-node cost | stateKey + legalActions + simulate per atomic step | stateKey + eval per turn-end state only |
| mouseSkill explosion | 27x per mouse turn | Absorbed into turn enumeration |

### Why it preserves rule exactness

- Turn-end states are enumerated using the SAME `simulateSearchAction` + `generateLegalSearchActions` + `forceEndTurnIfNeeded` — no rule changes.
- The only difference is WHEN minimax decisions are made: at turn boundaries instead of at every atomic step.
- Within-turn DP (dedup by stateKey) is equivalent to the current TT but applied at enumeration time, not search time.
- Chance nodes are handled identically (enumerate all outcomes).
- The minimax value is mathematically identical: MAX/MIN over turn-end states = MAX/MIN over all atomic-action sequences (since every sequence converges to a turn-end state).

### Expected impact

- **d1 cost drops dramatically**: from 86-154 internal + 214-347 leaves to 14-214 eval-only states
- **d2 cost drops**: from 571-4,283 nodes to ~14-214 × 10-615 = 140-131,610 state pairs (before AB)
- **AB becomes effective at d1**: turn-end states include both MAX (cat) and MIN (mouse) selections at d2, enabling cutoffs
- **d3 becomes feasible**: ~20-50x growth per turn-level depth (not per atomic step), so d3 ≈ d2 × 20-50 = 3K-200K, potentially achievable in 1-5 seconds
- **d4 may become feasible**: ~60K-10M, potentially achievable in 5-30 seconds

### Trade-offs

- Within-turn enumeration cost: BFS to enumerate all unique turn-end states adds overhead, but this is O(unique states) not O(raw sequences). For g4t2 cat turn: 140 expanded nodes (current) vs ~143 unique states (proposed) — similar. For mouse turn: 2,277 expanded (current) vs 255 unique (proposed) — 9x reduction.
- Memory: need to store the action sequence to each unique turn-end state (for plan extraction). Bounded by unique states per turn (~200-600).
- No rule changes: the search is still exact. The only approximation is if we add chance sampling (NOT recommended — would change math).

### Not recommended for this phase

- **CHANCE REDUCTION**: Chance is 0-3.4% of nodes — not the bottleneck. Any approximation would change math for negligible gain.
- **SELECTIVE DEEPENING**: The tree itself is not efficient enough — deepening a few critical lines won't help when the base tree is too expensive.
- **MOVE ORDERING improvement**: Already decent at d2 (high first-move cutoff rate). The problem is structural (d1 has no MIN), not ordering.
