## 3. Current policy implementation audit (read from real code, not names)

Source of truth: `src/game/engine.ts`, `src/game/ai/*`, `ai-training/ts-bridge/selfplay.ts`.
No code was changed.

### 3.1 How the bridge drives a game

`playGame()` builds `config = { ...DEFAULT_CONFIG, difficulty: <mapped> }`, then calls
`createInitialState(config)`. The difficulty mapping (selfplay.ts L337):

```ts
difficulty: catPolicy === 'medium' ? 'medium'
  : catPolicy === 'hard' || catPolicy === 'hard_explore' ? 'hard' : 'easy',
```

Per cat turn, `applyCatTurn(s, policy, rng)` loops `catMovesLeft` times and calls
`catAiMove(s)` (or `randomCatAction` / `hard_explore` mix). Per mouse turn,
`applyMouseTurn(s, policy, rng)` loops `mouseMovesLeft` and picks a direction via
`chooseMouseDir`.

### 3.2 Cat policies (real behavior)

| policy | config.difficulty | real decision logic | deterministic? | exploration |
|---|---|---|---|---|
| `easy` | easy | `catAiEasy`: BFS to mouse, box-push, **10% random alternate move** (engine.ts L1910 `Math.random() < 0.1`) | stochastic | 10% fixed, **global Math.random** |
| `medium` | medium | routing: not easy, not hard → `catAiHard` (legacy heuristic AI) | stochastic | **5% random** to 2nd-best (engine.ts L2125 `Math.random() < 0.05`) |
| `hard` | hard | `catAiMove` hard branch → `planHardCatTurn` (Expectiminimax iterative search), fallback `catAiHard` | algorithm-deterministic; **wall-clock deadline makes realized output run-to-run non-reproducible** | none explicit (search) |
| `hard_explore` | hard | `rng() < EPS_EXPLORE (0.15)` → `randomCatAction`, else `catAiMove` (hard search), **per cat step** | stochastic | **15% per-step**, using bridge **seeded Mulberry32 `rng`** (selfplay.ts L305) |
| `random` | easy (irrelevant) | `randomCatAction`: 15% place-trap if possible, else shuffled first legal `catMove` | stochastic | 100% random (by definition), **seeded `rng`** |

Critical routing detail (engine.ts L3334-3369): `catAiMove` sends `Easy → catAiEasy`,
`Hard → planHardCatTurn`, and anything else (incl. `Medium`) → `catAiHard`. So
`medium` runs the **legacy heuristic** `catAiHard`, NOT the search planner.

### 3.3 Mouse policies (real behavior)

| policy | real decision logic | deterministic? | randomness |
|---|---|---|---|
| `random` | shuffled `DIRECTIONS`, first legal `mouseMove`; **never uses skill** (selfplay.ts L258 gate `policy !== 'random'`) | stochastic | 100% random, **seeded `rng`** |
| `greedy` | if carrying butter and skill inactive and `rng() < 0.5` → `mouseSkill` (drop butter, +3 moves, unlock tunnels); then BFS toward hole (if carrying) or nearest butter; fallback first legal move | stochastic | 50% skill trigger, **seeded `rng`** |
| `greedy_skill` | **identical to `greedy` in current code** — same 50% skill gate (`policy !== 'random'`), same `chooseMouseDir` BFS; there is NO separate `greedy_skill` branch | stochastic | same as greedy |

**Finding G0.4B-0-1 (important):** `greedy` and `greedy_skill` are currently the **same
policy implementation**. The skill-trigger probability (0.5) and the greedy BFS are shared
verbatim. `greedy_skill` is a nominal label with no distinct code path today. Any
canonical selection that relies on `greedy_skill` being "stronger/smarter" would be
unsupported by the code.

**Finding G0.4B-0-2:** `hard_explore`'s epsilon applies **per cat step** inside a turn
(not once per turn), and it uses the bridge's **seeded** `rng` (reproducible given the
seed), whereas `easy`/`medium` exploration uses **global `Math.random`** (not reproducible).

**Finding G0.4B-0-3:** the **legacy mixed-mode bridge** calls `catAiMove(s)` **fresh on every
step** of the cat turn. For `hard`, each call re-runs `planHardCatTurn` (a fresh search).
This differs from the UI trajectory path (`computeCatAiTrajectory` plans once per turn).
For self-play, legacy-mode hard is therefore **re-searching per step**, which is both
slower and a subtly different policy from the single-plan-per-turn production path.
**RESOLVED by G0.4B-0P:** the **canonical-v1 mode** no longer uses `applyCatTurn`; it drives
the cat turn through the **production `computeCatAiTrajectory`** (one initial main plan per
turn + production fallback rules), replicating `GamePage.runCatAi` semantics. The legacy
per-step re-search path remains only in the historical mixed mode.

**Finding G0.4B-0-4:** any non-`random` cat policy that returns `null`/no-op **falls back
to `randomCatAction`** (selfplay.ts L308-311). So every cat policy has a tail of random
behavior when the AI gets stuck — an implicit, state-dependent randomness shared by all
policies.

### 3.4 Stationarity audit (answers to the task's 10 questions)

1. What production logic each policy calls → see tables above.
2. Deterministic / stochastic → `easy/medium/hard_explore/random` stochastic; `hard` algorithm-deterministic but timing-dependent.
3. Random tie-break? → `easy` 10%, `medium` 5%, `hard_explore` 15%, `random` 100%; `hard` search tie-breaks are deterministic (move ordering).
4. Exploration? → only `hard_explore` (15% per-step); `easy`/`medium` have small built-in randomness (10%/5%).
5. Exploration fixed probability? → yes: 0.15 / 0.10 / 0.05 are constants (EPS_EXPLORE, inline literals).
6. hard_explore vs hard → only difference is 15% per-step random action; both difficulty=hard (search AI).
7. greedy_skill vs greedy → **no code difference** (finding 1).
8. State-dependent randomness? → yes: `mouseSkill` only when carrying butter (0.5); trap placement only when no trap + traps remaining (0.15); fallback-to-random only when stuck.
9. Policy changes with game index / dataset progress? → **no**: the bridge picks a policy per game from fixed weights, but within a single dataset version nothing changes over time.
10. Non-stationarity mechanism? → `hard` wall-clock deadline (run-to-run variation) is the only non-stationary-by-implementation source; everything else is a **fixed stationary stochastic policy**.

Conclusion: the code supports defining a **stationary stochastic policy** for every
candidate, provided we (a) freeze all constants, (b) use one policy version per dataset,
and (c) document that `hard` is timing-nondeterministic.

## 5. Recommended canonical pair

**APPROVED_FOR_PILOT_ONLY (was PROPOSED_NOT_YET_APPROVED; upgraded by G0.4B-0P human gate):**

```
CAT_POLICY   = hard
MOUSE_POLICY = greedy
```

Status note: this pair is approved **only** to enter the 200-game production-parity pilot
(which has been run — see `G0.4B-0P-canonical-v1-pilot.md`). It is NOT approved for 10k
generation yet; that requires a separate gate after the pilot is reviewed.

Rationale (must be read together with §4):
1. **Aligned with the eventual goal.** The whole program is building a Hard cat AI.
   Learning `V_pi` under the `hard` generating policy is the most on-distribution target
   for the thing we ultimately want to improve. `easy`/`medium` produce a different
   policy family and would teach a less relevant value function.
2. **Single, fixed policy identity.** One cat policy, one mouse policy, no switching.
   This is the entire point of the canonical dataset (vs G0.4A-2's mixing).
3. **No reliance on the misleading `greedy_skill` label.** Since `greedy_skill` == `greedy`
   in code (finding 1), choosing `greedy` is the honest choice. It is the stronger mouse
   opponent relative to `random`, giving a non-trivial label distribution (≈0.80 cat win).
4. **Class balance is acceptable** (~0.80/0.20), and §15's game-balanced weighting handles it
   without re-mixing policies. `random` mouse is rejected (≈0.97-1.0 imbalance).
5. **hard_explore is deferred to a future policy version.** `hard_explore + greedy` (D) is
   the strongest diversity candidate and is a legitimately stationary stochastic policy,
   but introducing 15% random cat actions makes the target `V` under an intentionally
   sub-optimal cat. For canonical-v1 we want the cleanest teacher; exploration can be added
   later as `canonical-v2` (a NEW dataset version, never appended).

**Explicit non-selection notes:**
- `greedy_skill` is NOT selected as a distinct mouse policy because it has no distinct code path.
- `hard_explore` is NOT selected for canonical-v1 (exploration deferred to a versioned upgrade).
- `medium` is NOT selected (legacy heuristic, not the search AI).
- `random` mouse is NOT selected (extreme imbalance).

## 6. Stationarity / exploration contract

**Principle: canonical ≠ deterministic.**

A dataset version may use a **stationary stochastic policy** `pi(a|s)` with all random
rules and parameters fixed. Examples of allowed randomness:

- `hard` search is algorithm-deterministic but wall-clock-deadline-nondeterministic.
  Within a version we fix the search config (see §8) and accept the timing variation as
  part of the environment (it is a fixed policy definition, not a changing policy).
- **`hard` has a stochastic fallback tail (G0.4B-0P clarification):** when the planner
  produces no legal solution, production `catAiMove` falls back to `catAiHard`, which
  contains a real `Math.random() < 0.05` → 5% "second-best" randomness (engine.ts L2125).
  So **Hard is not purely deterministic** even ignoring the deadline; canonical-v1 must be
  described as a **stationary stochastic / timing-sensitive policy snapshot**, not
  "deterministic except deadline".
- `greedy` mouse has a fixed 0.5 skill-trigger probability using the seeded bridge `rng`.
  **Precise definition (G0.4B-0P):** at the **start of each eligible mouse turn**, if the
  mouse is carrying butter and skill is inactive, perform **one** Bernoulli(p=0.5) skill
  decision using the seeded Mulberry32 bridge RNG. It is NOT a per-step 50%. After that,
  `chooseMouseDir` drives every step by greedy BFS toward the current goal (hole if
  carrying, else nearest butter), falling back to the first legal move.

**Forbidden** (would break stationarity / re-create confounding):
- Changing epsilon / probabilities mid-dataset (e.g. first 2000 games 0.15, then 0.10).
- Switching cat or mouse policy identity per game within one dataset version.
- Mixing `easy/medium/hard/hard_explore/random` under one `TARGET` label.
- Adding "a bit of random cat" or "a bit of easy cat" to rebalance labels.

If any of these is desired, it must become a **separate dataset version** (see §7).

## 7. Target semantics contract

**TARGET_NAME = `CANONICAL_POLICY_OUTCOME`**

Formal definition:

> For a state `s` sampled under canonical joint policy `pi` (fixed cat + fixed mouse),
> the target `z` is the **terminal winner of continuing the sampled trajectory** under
> the **same fixed canonical joint generating policy `pi`**.

Encoding:
- `z = +1` cat win
- `z = -1` mouse win

The target is **NOT**:
- `evaluateForCat` score
- minimax / game-theoretic optimal value
- optimal continuation
- a handcrafted G4 label
- a policy id
- a mixed-behavior-policy outcome

**ValueNet input (STATE_ONLY) must NOT include generating-policy identity.** Because the
whole dataset shares one policy, the policy identity is a dataset-level constant and must
not appear as features (the one-hot would be constant → useless at best, confounded at worst).

**HARD_TRIAL freeze note (G0.4B-0P):** canonical-v1 freezes `HARD_TRIAL.refutationEnabled =

or any exploration parameter changes, you must create a **new dataset version**
(`canonical-v2`, ...). Never append new-policy data to an old version; never mix labels
across policy versions. Cross-version mixing is exactly the G0.4A-2 failure mode.

## 9. RNG / map-generation limitations (verified)

- Engine map generation (`createInitialState`, `generateBoxPositions`,
  `generateButterPositions`, `generateSingleButterPosition`) uses **global
  `Math.random()`**, which is **not seeded** and **not reproducible**.
- Project rule (verified in code + tests): `Math.random` is **never monkey-patched**.
  We will not change the engine RNG this stage or in B-1 without a separate decision.
- The bridge's **policy** RNG is a **seeded Mulberry32** (`rngFrom(seed + ...)`); it drives
  `hard_explore` epsilon, mouse 50% skill, and `random` action selection. This part IS
  reproducible given the seed.
- `mapInstanceId == gameId` is **NOT a reproducible seed**; it is only a per-game map
  instance id. The contract will state this explicitly in metadata.

**Consequence / honest limitation:** a canonical 10k dataset cannot be re-generated
**bit-identically** with the same maps (maps come from global `Math.random`). What IS
reproducible given a fixed seed: the policy decisions (which depend only on the seeded
bridge rng and the current state). We record this limitation; it does not block generation,
but it means "same seed → same policy RNG stream, different maps each run".

## 10. 10k dataset composition contract (design only)

**Definition: 10,000 RESOLVED games.** The existing pipeline writes only resolved games
(`playGame` returns null when `winnerSign === 0` after `MAX_TURNS=500`, and the loop
`while (writtenGames < perWorker)` keeps generating until the target count is written).

Handling rules (matching current code; proposals for any change are NOT executed now):
- `unresolved / MAX_TURNS` → **discarded** (return null), counted as attempts not written.
- `abnormal termination` → same discard path.
- `terminal winner` → written; all states of a game share the winner sign (patched at offset 10).
- `duplicate states` → currently kept (no dedup). Proposal for B-1: report duplicate-state
  rate; do not dedup (states are legitimate repeats across games).
- `extreme long games` → currently kept up to MAX_TURNS=500. Proposal: record max/mean length.

**Estimated size (from existing data1k, hard+greedy-ish pairs):**
- data1k: 1000 games → 15432 states → **≈15.4 states/game** overall (mixed).
- hard|greedy: meanGameLen ≈ 11.17 → ~11 states/game.
- hard|greedy_skill: ≈ 7.6 (n=15).
- hard|random: ≈ 27.9 (cat dominates, longer games).
- **Estimate for canonical-v1 (hard+greedy): ≈ 10k games × ~11 states ≈ 110k states**
  (range ~90k-130k; will vary with map luck).

**Estimate note:** this is an order-of-magnitude estimate from the mixed 1k; the real
canonical pair's mean length must be measured on a pilot before committing to exact counts.

## 11. Split contract

Two mechanisms exist and MUST NOT be conflated:

1. **Storage shard split (bridge):** `h = gameId % 10` → `h===0` heldout, `h===1` val,
   else train (selfplay.ts L500-503). This is **game-atomic** (whole game → one shard) but
   is a **storage layout**, not the evaluation split.
2. **Evaluation split (Python audit):** `grouped_stratified_split` — game-atomic, stratified
   by `(catPolicy, mousePolicy, winner)`, deterministic per seed. This is what G0.4A-2 used
   and what produces the reported held-out metrics.

**Canonical-evaluation contract for 10k:**
- The **Python grouped_stratified_split** (game-atomic, stratified by winner since policy is
  constant) is the **canonical evaluation split**. 5 seeds (20260826..20260830), same as
  G0.4A-2.
- The bridge storage shard is used only for physical storage of generated records; it is
  **not** a reporting split.
- **No game may span train/val/heldout** in either mechanism (already true in both;
  verified in `grouped_stratified_split` and `validate_schema.cross_split_gameids`).

## 12. Evaluator sidecar contract

The §14 bridge fix (already applied) is the required mechanism:

```
same authoritative live GameEngineState s:
  encodeState(s, ...)  -> record  (145 bytes)
  evaluateForCat(s)    -> sidecar (float32 LE, 4 bytes)
strict 1:1 per record.
```

Canonical dataset MUST produce (or the project's actual shard naming):
`train.bin` + `train_eval.bin`, `val.bin` + `val_eval.bin`, `heldout.bin` + `heldout_eval.bin`.

Integrity requirements:
- `record_count * 4 == sidecar_bytes` for each shard.
- Record ordering identical between `.bin` and `_eval.bin`.
- **Fail-fast** assertion `res.buf.length === res.evals.length` (already added in
  `playGame()`; the write loop is 1:1).
- Sidecar is **diagnostic only**: never a ValueNet target or feature; never used for
  checkpoint selection or early stopping.

## 13. Dataset purity contract

After generation, the dataset must be automatically provable:

```
CAT_POLICY_UNIQUE_COUNT   = 1
MOUSE_POLICY_UNIQUE_COUNT = 1
POLICY_VERSION_UNIQUE_COUNT = 1
```

If a second generating policy appears → `DATASET_PURITY = FAIL`.

Additional automatic checks:
- `winnerSign` only in {-1, +1}
- phase / terminal consistency (each game has exactly one winner sign; no mid-game terminal)
- record size consistency (all 145 bytes)
- game grouping integrity (all states of a game in one split; no cross-split gameId)
- sidecar count integrity (record vs eval 1:1)
- schema consistency (matches schema.json / REC layout)
- **G4 forensic exclusion**: G4 records never enter train/val/heldout
  (`forensic_g4_states.bin` is a separate file; `excludedFromTraining: true`).

## 14. Outcome balance contract

**Forbidden:** re-introducing mixed policies to balance win rates. If a canonical pair gives
cat 80% / mouse 20%, you must NOT "add some random cat", "add some easy cat", or "swap the
mouse policy" to rebalance — that recreates target confounding.

**Allowed:**
- game-balanced training weights (already implemented: `game_weights 'game_balanced'`)
- class weighting in loss
- larger dataset (more games, same policy)
- fixed-policy exploration (only as a versioned policy change, not within a dataset)
- future canonical policy redesign (as a NEW policy version)

Generating policy identity stays single within a dataset version.

## 18. Risks / unresolved questions

1. **hard is slow + timing-nondeterministic.** The canonical production-parity path measured
   **~1.34 resolved games/sec single-worker** on the 200-game pilot (vs ~0.21 games/sec for
   the old per-step mixed path). 10k games ≈ **~2.1h single-worker** at this rate (well
   within one session). Parallel generation remains FORBIDDEN for canonical-v1 unless a
   future TIMING_PARITY_BENCH shows worker-count parity; single worker is the default.
2. **greedy == greedy_skill in code.** Before any "skill mouse" version, decide whether to
   implement a truly distinct skill policy (new policy version) or drop the name.
3. **Map randomness is not reproducible** (global Math.random). Documented limitation;
   no engine change without a separate decision. Map DIVERSITY is measured by ACTUAL_MAP_FINGERPRINT
   (board terrain + hole + initial butter positions), NOT mapInstanceId. Pilot: 200/200 unique (100%).
4. **Class imbalance (~73/27 in pilot).** game-balanced weighting mitigates; may need a larger
   dataset than 10k if mouse-win tail coverage is insufficient. Unresolved.
5. **Bridge fallback-to-random tail** (finding 4) means even "hard" has occasional random
   actions when the AI is stuck. This is part of the policy; must be recorded, and the
   fallback rate should be measured as a B-1 gate (L). (Pilot: 0 SEARCH_FALLBACK / 0
   HARD_FALLBACK_MOVE across 961 cat turns — production hard found valid plans throughout.)
6. **Per-step re-search vs per-turn plan** divergence (finding 3) — **RESOLVED**: canonical-v1
   uses production `computeCatAiTrajectory` (one main plan per turn). The legacy per-step path
   remains only in historical mixed mode.
7. **HARD_TRIAL refutation sidecar is ON in the current build.** **FROZEN for canonical-v1**:
   refutationEnabled=true, totalTurnBudgetMs=150 (matches production call sites). Changing it
   later requires canonical-v2. Pilot measured: 716 refutation-triggered / 25 overrides /
   4296 candidates across 961 cat turns.
8. **Number of states estimate.** The 200-game pilot measured **mean 10.0 states/game**
   (median 7, p95 26, max 56) → 10k games ≈ **~100k states**. Better than the rough G0.4B-0
   estimate. Balance measured at 73% cat / 27% mouse. (Pilot is now run; these are measured,
   not estimated.)

## Core questions answered

- **Q1** Why was the mixed-policy 1k target polluted? → The generating distribution mixed
  cat policies (easy/medium/hard/hard_explore/random) and mouse policies
  (random/greedy/greedy_skill) across games. G0.4A-2 proved policy identity alone predicts
  outcome (POLICY_ONLY AUC 0.828; +0.210 from adding policy one-hots). The label therefore
  encodes "who generated this", not pure state value.
- **Q2** How does a canonical dataset eliminate policy-identity confounding by construction?
  → One fixed cat policy, one fixed mouse policy, one policy version, one stationary
  stochastic policy per dataset; policy identity is a dataset constant and never a feature;
  no mixing within a version (§6, §7, §8, §13).
- **Q3** Recommended cat policy → `hard` (APPROVED_FOR_PILOT_ONLY).
- **Q4** Recommended mouse policy → `greedy` (APPROVED_FOR_PILOT_ONLY).
- **Q5** Why these, not others → Aligned with the eventual Hard-AI goal; honest about
  `greedy_skill`==`greedy`; avoids extreme imbalance of `random` mouse; defers exploration
  to a future version; `medium` is a legacy heuristic not the search AI (§5).
- **Q6** Deterministic or stationary stochastic? → stationary stochastic / timing-sensitive
  snapshot (hard: one production plan per turn + wall-clock nondeterminism + 5% catAiHard
  fallback tail; greedy: one Bernoulli(0.5) at turn start + greedy BFS).
- **Q7** All exploration/randomness params → cat: none explicit on normal path, catAiHard
  fallback 5% (global Math.random), stuck-fallback random; mouse: one Bernoulli(0.5) skill
  at turn start + greedy BFS + first-legal fallback, all via seeded bridge rng; MAX_TURNS=500
  discard; HARD_TRIAL refutationEnabled=true / 150ms.
- **Q8** May policy vary within a dataset version? → **NO.**
- **Q9** Policy upgrade path? → new policy version + new dataset version (never append/mix).
- **Q10** Math/semantic definition of the 10k target → `z` = terminal winner of the sampled
  trajectory under the fixed canonical joint policy; learned quantity is an estimate of
  `E[z | s, pi]` (a Monte-Carlo trajectory outcome, not an exact counterfactual value).
- **Q11** Is 10k authorized to generate now? → **NO.**
